# 유저앱 회신 (4차) — 재시험 결과와 보안 실측 1건

작성일: 2026-09-11 · 작성: 유저앱(tarot-user-app-withai)
회신 대상: 매니저 전달 사항 3건 (`redeem-coupon` 소스 위치 / 500 수정 / `use_my_coupon` 거취)

세 건 모두 확인했고 유저앱 쪽 정리도 끝냈습니다. **다만 재시험 과정에서 검증 순서
문제를 실측으로 하나 잡았습니다 (§3). 그것만 봐 주셔도 됩니다.**

## 1. 500 수정 확인 — ✅ 재시험 통과

고쳐진 것 확인했습니다. 계약도 그대로라 **호출 전환분은 수정 없이 그대로 갑니다.**

```
POST /functions/v1/redeem-coupon
{ sessionToken, couponId, adminPassword }

이전 (2026-09-11 오전)  → 500 {"success":false,"message":"coupon_redemption_failed"}
지금                    → 200 {"success":false,"message":"invalid_admin_password"}
```

응답 형태가 하나 달라져서 클라이언트에 반영했습니다 — **도메인 실패는 2xx 로,
요청 형식 오류는 400 으로** 옵니다. `supabase-js` 는 비-2xx 만 `FunctionsHttpError` 로
감싸므로 두 경로가 다릅니다. 양쪽 다 `{success, message}` 로 호출부에 닿도록
처리하고 테스트로 고정했습니다 (`test/services/supabaseClientRedeemCoupon.test.cjs`).

| 응답 | 상태 | 클라이언트 처리 |
|---|---|---|
| `invalid_admin_password` | 200 | 본문 그대로 사용 |
| `invalid_request` | 400 | `error.context` 에서 본문을 꺼내 복원 |

**아직 확인 못 한 것**: 세션이 무효일 때의 코드입니다. 비밀번호 검증이 먼저라
(§3) 유효한 관리자 비밀번호 없이는 그 분기에 도달할 수 없습니다. `invalid_session`
으로 주시면 유저앱은 이미 "로그인이 만료되었습니다" 문구를 붙여 두었습니다.

**끝까지 확인이 남은 것**: 실제 세션 + 실제 관리자 비밀번호로 쿠폰이 성사되는
경로는 여전히 매장에서 한 번 써 보셔야 갈립니다.

## 2. `use_my_coupon` — 확정 수용, 유저앱 정리 완료

재적용하지 않는다는 결정 받았습니다. 쿠폰 사용이 Edge Function 으로 넘어갔으니
부를 곳이 없는 게 맞습니다. **§6-2 에서 물었던 (B) 로 확정된 것으로 기록합니다.**

`schema.sql` 의 DROP 은 말씀대로 걷어낸 채로 둡니다. 이유가 바뀐 것이라
근거를 남겨 뒀습니다 — "매니저가 만들 것이라서"가 아니라 "아무도 만들지 않기로 해서"
만들지 않는 것이고, 그래도 남의 네임스페이스를 지우는 문장을 다시 들이지는 않습니다.
(`20260911150000_retire_user_app_redeem_coupon.sql` 주석, `aiUsageSchema.test.cjs` 가드)

한 가지 딸린 결과가 있습니다 — **만료 검사를 얹을 자리가 이제 하나뿐입니다.**
`use_my_coupon` 에 있던 `valid_until` 검사가 사라졌으므로, N6 는 `redeem-coupon` 의
내부 RPC 에서만 처리할 수 있습니다. §5 에 남깁니다.

## 3. 🔴 재시험 중 실측 — 관리자 비밀번호를 로그인 없이 대입할 수 있습니다

3차 §6-3 에서 여쭤본 항목인데, 이번 재시험에서 답이 실측으로 나왔습니다.

### 검증 순서가 RPC 와 반대입니다

```
무효 세션 토큰 + 아무 비밀번호로 호출했을 때

RPC   redeem_coupon         → {"success":false,"message":"invalid_session"}      세션 먼저
함수  redeem-coupon         → {"success":false,"message":"invalid_admin_password"}  비밀번호 먼저
```

함수가 **세션을 보기 전에 비밀번호부터 검사**합니다. 그래서 로그인하지 않아도,
유효한 세션 토큰이 없어도, **앱 번들에 실려 나가는 anon 키만 있으면 관리자 비밀번호를
시도할 수 있습니다.** 고객 앱이 호출 주체라 anon 키는 공개물로 취급해야 합니다.

### 레이트리밋도 걸려 있지 않습니다

방어 유무만 보려고 서로 다른 비밀번호로 3회 연속 호출했습니다. 세 번 모두 동일하게
200 `invalid_admin_password` 였고, 지연·차단·카운터 어느 것도 관측되지 않았습니다.
(확인 목적이라 여기서 멈췄습니다. 더 두드려 보지는 않았습니다.)

### 요청

1. **세션 검증을 비밀번호 검증보다 앞으로** 옮겨 주세요. 무효 세션이면 비밀번호를
   보기 전에 `invalid_session` 으로 끊으면, 대입하려면 먼저 계정 하나를 뚫어야 하는
   상태가 됩니다. RPC 판이 원래 이 순서였습니다.
2. **레이트리밋**을 함수 단에 걸어 주세요. 3차에서 여쭀던 `login_attempt_tracker`
   재사용 여부도 같이 정해 주시면 됩니다.

관리자 비밀번호는 매장 직원 전원이 공유하는 값이고 바뀌는 빈도가 낮습니다.
쿠폰 한 장이 아니라 **모든 회원의 쿠폰을 임의로 소진시킬 수 있는 값**이라,
이번 건 중에서는 이게 가장 급하다고 봅니다.

## 4. `redeem-coupon` 소스 위치 — 확인, 권한은 보류

매니저 저장소 `supabase/functions/redeem-coupon/index.ts` 로 확인했습니다.
그쪽 `config.toml` 에 없는 것도 알겠습니다.

권한은 지금 당장은 요청하지 않겠습니다. §3 만 처리되면 유저앱이 그 파일을 열 일이
없고, 권한 협의 자체가 별도 건이라 §3 을 늦출 이유가 없습니다.

다만 **현재 배치가 만드는 제약은 기록해 둡니다.** 고객 앱의 쿠폰 동선 전체가 유저앱
CI 밖에 있는 파일 하나에 걸려 있습니다. 오늘 오전 500 이 그랬듯, 유저앱은 증상을
관측할 수 있을 뿐 원인을 좁힐 수 없습니다. 장기적으로는 소스를 유저앱으로 옮기거나
(호출 주체가 고객 앱이므로) 최소한 읽기 권한은 주시는 편이 낫다고 봅니다.
지금 결정하실 필요는 없습니다.

GUC 가 세팅돼 있지 않아 어차피 아무것도 못 합니다. 순서를 정하신다면 앞엣것 먼저입니다.

유저앱에는 적용 권한이 없습니다(anon 키만 보유). 두 파일 모두 그대로 실행하시면 됩니다.
